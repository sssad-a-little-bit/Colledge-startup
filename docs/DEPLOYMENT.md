# Развёртывание и эксплуатация

## Граница готовности

Этот проект — демонстрация. До production необходимы проверки на целевой инфраструктуре, независимый обзор безопасности, согласование прав и обработки персональных данных, проверенное восстановление и эксплуатационный ответственный. Публикация и подключение реальных систем этой работой не выполняются.

## Развёртывание Node.js + PostgreSQL

1. Подготовьте выделенную БД PostgreSQL 17 с `btree_gist`; миграционная роль должна иметь право устанавливать это расширение. Приложение не должно работать под суперпользователем.
2. Создайте отдельные роли владельца миграций и приложения. Роли приложения необходимы только DML-права на рабочие таблицы и последовательности; не давайте ей изменение схемы и отключение триггеров. Обычный Compose использует владельца БД ради воспроизводимого локального запуска — это не production-политика.
3. Установите зависимости `npm ci`, задайте секреты через защищённое окружение, выполните миграции один раз `npm run db:migrate`. Проверяйте резервную копию перед миграцией. Seed в production не запускается.
4. Выполните `npm run build`, затем `npm start` под непривилегированным пользователем. `start` проверяет наличие и формат конфигурации. Не используйте dev-сервер для эксплуатационных измерений.
5. Поставьте HTTPS reverse proxy, `NEXTAUTH_URL` должен соответствовать внешнему адресу. Ограничьте размер запроса (например, 512 KiB для текущих текстовых форм), таймаут тела и частоту запросов на proxy; согласуйте их с серверными лимитами импорта. PostgreSQL наружу не публикуется.
6. Секрет `NEXTAUTH_SECRET` — случайный, не менее 32 символов; ротация завершает старые сессии. Никогда не используйте build-placeholder Dockerfile как runtime-секрет.
7. Создайте первый реальный административный аккаунт по отдельной согласованной процедуре. Демонстрационные аккаунты и известные пароли не переносятся.

`DATABASE_URL` должен включать разумный лимит пула, например `connection_limit=8&pool_timeout=10&connect_timeout=5` для небольшого экземпляра; итоговые значения зависят от числа процессов и `max_connections`. Поставьте `statement_timeout` и `idle_in_transaction_session_timeout` на роль БД после проверки длительности миграций и импорта. Не повторяйте неидемпотентную запись оценки автоматически.

## Docker-образ приложения

```bash
docker build -t kit-campus:local .
```

Образ использует закреплённую версию Node.js, выполняет build и работает от `node`. Секреты передаются только при запуске. Миграции запускаются отдельной одноразовой задачей в той же сети. Dockerfile включает инструменты миграций; оптимизация размера образа и проверка уязвимостей являются отдельной эксплуатационной работой. При сборке в сети с корпоративным CA передавайте доверенный CA штатным механизмом сборки; не отключайте проверку TLS.

Пример запуска приложения при уже доступной отдельной PostgreSQL:

```bash
docker run --rm --name kit-campus --env-file .env -p 127.0.0.1:3000:3000 kit-campus:local
```

Внутри контейнера `localhost` — сам контейнер, поэтому `DATABASE_URL` должен указывать доступное из него имя БД. Не публикуйте сервис без TLS и проверки конфигурации.

## Проверки и мониторинг

- `GET /api/health/live` проверяет живой процесс независимо от БД.
- `GET /api/health/ready` проверяет подключение к БД; при недоступной зависимости возвращается неуспех без внутренней строки подключения.
- Контролируйте коды HTTP и задержки, ошибки readiness, рестарты, заполнение диска, доступные соединения PostgreSQL, возраст последней копии и последнего успешного испытания восстановления.
- Серверные ошибки имеют request ID. Сопоставляйте его с ограниченными структурированными логами. Не собирайте тела форм, пароли, cookies, токены, значения оценок и экспортные файлы в общие логи.
- Персональные ответы не должны кешироваться CDN или общим reverse proxy. Настройка общего proxy не должна переопределять `private/no-store` приложения.
- Наличие одной машины, одного PostgreSQL и локального диска создаёт единую точку отказа; Compose не обеспечивает автоматическую отказоустойчивость.

## Резервное копирование

В комплекте `scripts/backup.sh`, `scripts/restore-check.sh` и `scripts/demo-restore.sh`. Последний сохраняет новую БД `campus_demo_restore_*` для повторяемого запуска демонстрации, не заменяя уже существующие БД. Используется `pg_dump --format=custom`, отдельный файл контрольной суммы, права `0600` через `umask`. Восстановление создаёт **новую временную БД**, проверяет основные количества и контрольные суммы учебных записей и удаляет только созданную временную БД. Исходная БД не заменяется.

```bash
export COMPOSE_PROJECT_NAME=kit-demo
bash scripts/backup.sh
bash scripts/restore-check.sh backups/<снимок>.dump
```

Для корректного сравнения с источником остановите записи на время копирования и проверки. Иначе изменения после `pg_dump` могут обоснованно вызвать различие. `BACKUP_DB`, `BACKUP_USER` и `BACKUP_DIR` настраивают локальный скрипт. Если БД запущена отдельным контейнером, задайте `BACKUP_CONTAINER=<имя>`: скрипты используют `docker exec` вместо Compose. Например, для изолированной тестовой БД `campus_demo`: `BACKUP_CONTAINER=kit-campus-db BACKUP_DB=campus_demo bash scripts/backup.sh`. Этот же набор переменных нужен для `restore-check.sh`. Право `CREATEDB` нужно только учётной записи проверки в изолированной среде, не веб-приложению.

Копии содержат чувствительные данные и password hashes: доступ ограничен, для production требуется шифрование, отдельное хранилище, политика хранения и контролируемый доступ. Копия на том же диске не защищает от потери узла. Наличие dump без успешного восстановления не считается проверкой. Реальный результат приведён только в TEST_REPORT.

Файловых вложений в этом контуре нет. При их добавлении потребуется отдельная копия закрытого файлового хранилища, согласованный снимок с БД и испытание восстановления ссылок и прав.

## Отказ и восстановление

1. Определите сбой по readiness и request ID, не публикуя секреты.
2. Остановите записи, сохраните диагностику без содержимого оценок и токенов.
3. Восстановите последнюю проверенную копию в новую БД, проверьте основные сущности, связи и чтение по каждой роли.
4. Переключите приложение, проверьте readiness, войдите заново и выполните безопасный сквозной сценарий.
5. Сообщите ответственным реальную потерю данных и время восстановления; не выводите эти величины из предполагаемых целей.

Предлагаемые для согласования RPO/RTO и доступность приведены в PILOT, фактические испытания — в TEST_REPORT. Гарантии 100% доступности нет.
